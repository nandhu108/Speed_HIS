# Module Spec — Nursing (Phase 10)

Status: **complete** (2026-07-17). Owns admission-scoped nursing charting (structured
assessments, shift-tagged notes, Pain/Fall-Risk(Morse)/Bed-Sore(Braden) risk scores with
auto-calculated bands, nursing care plans, transfer notes), the Medication Administration
Record (due-time schedule generated from IPD's medication orders; administer/skip/refuse with
reason; double-verification for high-alert drugs), ward-level per-shift SBAR handovers, and
incident reporting (report → review → close). Vitals and Intake/Output stay on Phase 9's
existing `ipd.ip_vitals`/`ipd.intake_output_entries` tables — this phase adds the entry points
the plan calls "feeds charts," not new tables, since those were already built basic-but-real
in Phase 9.

## Database (schema `nursing`)

| Table | Notes |
|---|---|
| `nursing.nursing_assessments` | Admission-scoped, repeatable. `TemplateCode` is free text like `IntakeOutputEntry.Category` — no template master; `DataJson` (jsonb) carries the answers, shape owned by the frontend per code. |
| `nursing.nursing_notes` | Shift-tagged notes (`NursingShift`: Morning/Evening/Night) — deepens IPD's plain, doctor-only `ProgressNote` with a nurse/shift lens. |
| `nursing.risk_assessments` | Pain / Fall Risk (Morse) / Bed Sore (Braden). `ScoreDataJson` (jsonb) holds the raw per-item scores the frontend submitted; `TotalScore`/`RiskLevel` are computed server-side by `NursingMath.SumScore`/`ResolveRiskLevel` so the banding rule lives in one testable place, not duplicated per caller. |
| `nursing.care_plans` | Problem/Goal/Interventions + `CarePlanStatus` (Active/Resolved). `ResolveAsync` sets `EvaluationNotes`/`ResolvedAt`; no re-opening once resolved. |
| `nursing.transfer_notes` | Nursing handover note accompanying a ward/room/bed transfer. `BedAllocationId` is optional (FK to `ipd.bed_allocations`) — a transfer note can also be filed for a consultant-only or status change with no bed move. |
| `nursing.mar_schedules` / `mar_administrations` | MAR. `MarSchedule` is one due-time row per `MedicationOrder`, lazily generated by `MarService.GetAsync` the first time a given admission/date is asked for (idempotent — regenerating skips due times that already exist). `IsHighAlert` snapshots `Drug.IsHighAlert` at generation time so a later master edit doesn't silently change an in-progress schedule's verification requirement. `MarAdministration` is the 1:1 action taken (Administered/Skipped/Refused) — `Reason` required for Skip/Refused, `VerifiedByUserId` required (and must differ from the actor) when the schedule row `IsHighAlert`. |
| `nursing.shift_handovers` / `patient_handover_notes` | Ward-level (branch-scoped directly, like `Admission`/`Bill`), one per ward/date/shift enforced by a partial unique index. `PatientHandoverNote` is the per-patient SBAR (Situation/Background/Assessment/Recommendation) line, cascade-deleted with its parent. |
| `nursing.incidents` | Branch-scoped directly. `PatientId`/`AdmissionId` are both optional — an incident can be staff/visitor/general with no patient involved. Lifecycle: Reported → UnderReview → Closed (`ReviewAsync`/`CloseAsync`); Phase 20 (Quality/NABH) later merges this into the org-wide register with RCA/CAPA — nothing here is wired to that yet. |

Cross-cutting addition in this phase's migration: `Drug.IsHighAlert` (Masters, Phase 2) —
drives the MAR double-verification rule; exposed end-to-end through `DrugService`/`DrugsPage`
as a normal editable master field, not a placeholder.

Migration: `Phase10_Nursing`.

## MAR due-time generation is a small, deliberately incomplete lookup

`NursingMath.GenerateDueTimes(frequency, startDate, endDate, forDate, orderedAt)` maps common
Indian-hospital frequency shorthand (OD/BD/TID/QID/Q6H/Q8H/Q12H/HS) to fixed clock times — no
drug-frequency master exists (`MedicationOrder.Frequency` is free text, same loose-coupling
posture as everywhere else). `SOS` (as-needed) and unrecognized codes generate nothing —
administration for those is recorded ad hoc, not against a generated schedule. `STAT`
generates exactly one due time: the moment the order was placed, only on the order's own date.
`MarService.GetAsync` calls this per admission/date on read and inserts any missing rows before
returning the joined schedule — there is no background job.

## Double-verification is enforced, not just flagged

`MarService.ActionAsync` refuses to record an `Administered` action against a high-alert
schedule row unless `VerifiedByUserId` is supplied **and** differs from the acting user — a
single nurse cannot self-verify. Skip/Refuse always requires a `Reason`; re-actioning an
already-actioned row (`Status != Pending`) is rejected. None of this touches Pharmacy stock —
MAR administration doesn't decrement stock or create an `Issue`; that link isn't wired up.

## Charting stays a plain save; only branch-scoped list reads add filters

Every admission-scoped charting write (assessment/note/risk score/care plan/transfer note) is
a single `SaveChangesAsync` after an active-admission check — same posture as Phase 9's
`ClinicalChartService`, since none of it touches stock, billing, or bed state. `ShiftHandover`
and `Incident` are the only two entities in this phase that carry `BranchId` directly (like
`Admission`/`Bill`) rather than inheriting scope through a parent; both are transactional,
top-level records that need to be listed/filtered without a join.

## Endpoints (`/api/v1/nursing`)

- `admissions/{admissionId}/assessments`, `/notes`, `/risk-assessments?type=`, `/care-plans`,
  `/care-plans/{id}/resolve`, `/transfer-notes`: `GET`, `POST` each (as applicable)
- `mar?admissionId=&date=`: `GET` (lazily generates the day's schedule);
  `POST mar/{id}/administer` (body carries `Action`: Administered/Skipped/Refused)
- `handovers/ward-patients?wardId=`: `GET` (prefill helper — the ward's current patients)
- `handovers`: `GET?wardId=&date=`, `GET {id}`, `POST` (create)
- `incidents`: paged `GET`, `POST` (report), `POST {id}/review`, `POST {id}/close`

## Permissions

`NURSING.CHART.{VIEW,MANAGE}` (assessments/notes/risk scores/care plans/transfer notes),
`NURSING.MAR.{VIEW,ADMINISTER}`, `NURSING.HANDOVER.{VIEW,MANAGE}`,
`NURSING.INCIDENT.{VIEW,CREATE,REVIEW}`.

## Frontend

- Admission-scoped charting lives as a "Nursing" tab inside IPD's
  `AdmissionDetailPage` (`/ipd/admissions/:id`) — sub-tabbed: Shift Notes, MAR (date picker +
  administer/skip/refuse, high-alert dose flagged with a double-verification prompt), Risk
  Scores (scale picker with the real Morse/Braden item sets, banded result badge), Care Plans,
  Assessments (template picker + free-text findings), Transfer Notes. Kept inline in the same
  file as IPD's other tabs (Progress Notes/Vitals/etc.) rather than split into the `nursing`
  feature folder, matching that file's existing single-file-per-tab convention.
- `src/features/nursing/pages/ShiftHandoversPage` (`/nursing/handovers`) — ward + date filter,
  list, detail modal (SBAR per patient), create modal that pulls the ward's current patients
  (`ward-patients`) to prefill per-patient SBAR rows.
- `src/features/nursing/pages/IncidentsPage` (`/nursing/incidents`) — status-filtered paged
  list, detail modal, report modal (type/location/severity/description/immediate
  action/optional patient link via the shared `PatientPicker`), inline review/close actions.

## Deferred / notes

- **MAR frequency lookup is intentionally small.** Only OD/BD/BID/TID/TDS/QID/QDS/Q6H/Q8H/
  Q12H/HS/STAT/SOS are recognized; anything else (e.g. alternate-day "QOD") generates no
  schedule rows today rather than guessing.
- **MAR now optionally decrements Pharmacy stock (added 2026-09-16, closing a gap flagged in
  `docs/PATIENT_JOURNEY_GAP_ANALYSIS.md` §4.6).** `MarAdministration` gained nullable
  `BatchId`/`Quantity`; when a nurse picks a batch while confirming an `Administered` dose,
  `MarService.ActionAsync` (now wrapped in `IUnitOfWork.ExecuteInTransactionAsync`, since it
  can touch stock) writes an `IssueOut` `StockLedger` row against that batch — the same
  "document is its own reference" idiom OT's `ImplantUsage`/`ConsumableUsage` already use
  (`ReferenceType = nameof(MarAdministration)`), not a new `Issue` header. **The batch link
  stays optional on purpose**: a nurse can always confirm a dose with no stock effect, since
  clinical charting must never be blocked by an inventory problem (no matching batch, wrong
  store, forgot to check) — `MarScheduleDto.Administration.StockDeducted` (derived from
  `BatchId != null`, not its own stored column) tells the UI/reports whether this particular
  dose's consumption was actually tracked. If a batch *is* picked, insufficient stock on that
  batch still throws (same as Pharmacy's own sale/issue validation) — the nurse either picks a
  batch with enough on hand or leaves it untracked, there's no silent partial deduction.
  Quantity is a free `decimal` the nurse enters (defaults to 1 in the UI) — `MedicationOrder.Dose`
  stays free text ("500mg"), there's still no structured dose-to-stock-unit conversion.
- **`ShiftHandover.HandoverToUserId` isn't set from the UI.** The API supports naming who the
  shift is handed to, but the create form leaves it null (populating a user picker would need
  `ADMIN.USER.VIEW`, which a bedside nurse role may not hold) — it can be added by a future
  pass that resolves the permission question.
- **Incident reporting has no RCA/CAPA fields.** Deliberately shallow per plan §10 ("links to
  Quality module later") — Phase 20 (Quality/NABH) is where severity-driven routing, root
  cause analysis and corrective-action tracking land.
- **Nursing assessments have no structured form builder.** `TemplateCode` + `DataJson` are
  schema-ready for real structured templates per code, but the current UI only captures a
  single free-text "findings" field wrapped as `{"notes": "..."}` — a genuine form builder is
  future work, not a Phase 10 deliverable.
- **MAR was 500ing on every read (fixed 2026-09-17, pre-go-live QA audit).** The
  `20260916094354_Nursing_MarStockLink` migration (the `BatchId`/`Quantity` columns above) had
  never been applied to the running dev database, so `MarService.GetAsync`'s
  `Include(a => a.Batch)` failed with `column m2.batch_id does not exist` on every
  `GET /nursing/mar` call, for every admission. This was an unapplied-migration/environment gap,
  not a code defect — the migration file itself was already correct. Applied it directly against
  the dev DB (`nursing.mar_administrations` now has `batch_id`/`quantity` plus the FK/index, and
  `__EFMigrationsHistory` records it) so the MAR sub-tab and administer/skip/refuse actions work
  again; no source change was needed.
